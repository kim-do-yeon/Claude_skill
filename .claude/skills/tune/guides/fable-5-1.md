# Fable 5.1 (Mythos 5.1) 튜닝 가이드

출처: platform.claude.com "Prompting Claude Fable 5.1", "What's new in Claude Fable 5.1". 아래는 튜닝 시 적용할 규칙.
Mythos 5.1은 Fable 5.1과 같은 역량이며 검증 프로그램(사이버 검증 등)을 통과한 조직에만 제공된다.

## 핵심 성향
기존 Fable 5 프롬프트로도 잘 동작하며, Fable 5 가이드의 원칙(짧게 지시, 이유를 줌, 경계 명시, 메모리 파일 활용)은 그대로 유효하다.
목표가 분명하면 방법론 지시 없이도 아주 긴 작업을 수행한다. 대신 5.1에서 달라진 성향이 몇 가지 있어 아래 규칙으로 보정한다.

## 튜닝 규칙
1. **짧고 이유 있는 지시.** 지시 이행력이 강해 간결한 한 줄로 잘 조종된다. 행동을 일일이 열거하지 말고 왜 시키는지 맥락을 준다.
2. **작업을 끝까지 하게 한다.** 비동기·장기 작업에서 다음 할 일을 설명만 하고 턴을 끝내거나("다음으로 …하겠습니다"), 이미 요청된 단계에 허락을 구한다("적용할까요?"). 자율 실행이면: "사용자는 실시간으로 보고 있지 않아 중간 질문에 답할 수 없다. 원 요청에서 따라 나오는 되돌릴 수 있는 행동은 묻지 말고 진행. 파괴적 행동·실질적 범위 변경에서만 멈춘다. 턴을 끝내기 전 마지막 문단이 계획·다음 단계·약속이면 지금 도구로 수행하라". 단, 사용자가 문제를 설명하거나 질문만 한 경우엔 산출물이 '평가'이므로 보고하고 멈추게 한다.
3. **범위 = 산출물.** "요청(또는 승인된 계획)이 범위다. 조용히 좁히거나 넓히거나 바꾸지 말 것. 판단이 갈리면 일상적 판단은 스스로, 해석에 따라 작업이 크게 달라질 때만 확인. 한 부분이 막히면 나머지를 전부 끝내고 무엇을 왜 뺐는지 말한다".
4. **요청 밖 수정·테스트 억제.** 열린 기능 구현에서 주변 코드를 고치거나 동작을 확장하고 테스트 파일을 과하게 커밋한다: "작업 중 발견한 기존 버그·성능 문제·언급 안 된 동작은 요청 동작에 필수가 아니면 고치지 말고 요약에 후속 과제로 보고. 모호하면 문구와 주변 코드가 가장 직접 지지하는 해석 하나만 구현하고 그 가정을 밝힌다. 테스트는 요청했거나 레포 관행일 때만, 이웃 테스트 크기로. 요청된 동작은 전부 완전히 구현".
5. **진행 업데이트를 요청한다.** Fable 5보다 장시간 도구 호출 중 업데이트가 적다(높은 effort일수록 심함). "숨기고 최종 응답에 모아라"류 억제 문구를 먼저 지우고, 필요하면 "시작 전 한 줄로 할 일, 작업 중 짧은 업데이트, 끝에 마지막 메시지만 봐도 전체가 이해되는 요약(발견·수행·다음 단계)"을 넣는다.
6. **독립 도구 호출 묶기.** 코딩·computer-use 루프에서 암묵적으로 이어지는 독립 호출을 턴마다 하나씩 할 수 있다: "다음에 필요한 것을 먼저 속으로 나열하고, 서로의 결과에 의존하지 않는 것은 이번 응답에서 한꺼번에 요청하라".
7. **문체 밀도 완화.** 문장이 길고 문단 구분이 적어질 수 있다. 산문 산출물이면 "꾸민 문체(은유·수사로 직접 진술을 대신하는 것)를 빼고 문자 그대로 말하라"를 넣는다.
8. **서식 규칙은 '언제 쓸지'로.** 5.1은 볼드·헤더·리스트를 덜 쓰는 쪽이다. 기존의 반(反)서식 문구는 지우고 "내용이 다면적이거나 요청 시 리스트 사용, 최소 서식 요청 시 전면 생략, 대화·감정적 교류는 평문"처럼 쓴다.
9. **출처 인용 표시.** 문서 요약 시 원문을 인용 표시 없이 옮기는 경향이 있다. 요약·비교 작업이면 "출처 내용은 자기 말로 간접 서술하고, 원문 그대로 쓰는 짧은 구절만 따옴표로 표시"를 넣는다(가능하면 올바른 응답 예시 1개).
10. **최신 정보는 검색 강제.** low effort에서 검색 대신 기억으로 답하는 경향: "확신 없이 아는 이름이나 AI 모델·개발 도구처럼 빠르게 변하는 분야의 이름은 답하기 전에 사용자가 쓴 표기 그대로 검색하라".
11. **작은 변경은 부분 편집.** 작은 수정에도 파일 전체를 다시 쓰는 경향: "결과가 같다면 파일 전체 재작성 대신 필요한 부분만 편집하라".
12. **비전 작업엔 크롭/줌 도구.** 조밀한 차트·이미지는 반복 분석·크롭·검증 도구를 줄 때 최고 성능.
13. **오탐 줄이는 표현.** "컴파일 에러 없이 컴파일되나?" 대신 "이 프로그램에 버그가 있나?"로 묻는다. 덜 알려진 언어면 언어 설명·문서를 붙인다. 도구 출력에 base64 데이터를 넣지 않는다.

## 하지 말 것
- **"네 추론을 응답에 재현/설명하라"류 지시 금지.** `reasoning_extraction` 거부를 부른다. 짧은 근거·작업 요약 요청은 괜찮다.
- **반(反)서식·나레이션 억제 문구 유지 금지** (규칙 5·8).

## 설정·라우팅 (프롬프트 본문 아님 → ※ 메모로만)
- effort가 1차 제어. **기본 `high`**에서 시작해 low/medium/xhigh/max를 자체 평가로 재스윕(Fable 5와 레벨 의미가 다름). medium ≈ Fable 5 수준을 더 싸게, low도 Opus·Sonnet 대비 경쟁력.
- low에선 검색 호출이 줄고, xhigh/max에선 긴 산출물을 thinking에서 먼저 초안 잡느라 느려지고 `max_tokens`에 걸릴 수 있다 → 긴 산출물은 high 권장.
- thinking **항상 on**(adaptive 전용). `budget_tokens`/`disabled`는 400 에러. 컨텍스트 1M, 최대 출력 128k.
- 대화 이력은 append-only로 유지(이전 턴 편집 시 thinking 블록 바인딩 400 가능). 턴 단위 리마인더는 turn-scoped system message로.
- 안전 분류기 거부 시 `stop_reason: "refusal"`. 서버측 fallback을 켜면 Opus 4.8/Opus 5로 재시도될 수 있어 실제 응답 모델이 달라질 수 있다.
