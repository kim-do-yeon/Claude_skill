# Sonnet 5.5 튜닝 가이드

출처: platform.claude.com "Prompting Claude Sonnet 5.5", "What's new in Claude Sonnet 5.5". 아래는 튜닝 시 적용할 규칙.

## 핵심 성향
기존 Sonnet 5 프롬프트로도 잘 동작하며 Sonnet 5 가이드의 원칙(리터럴 이행 → 범위 명시, 부정 지시보다 긍정 예시)은 유효한 출발점이다. 최난도 장기 작업은 Opus가 더 낫다.
**effort 수준이 행동을 크게 바꾼다**: low/medium에선 코딩 작업 도중 확인하러 멈추거나 검증을 건너뛰고, xhigh/max에선 요청 이상으로 리뷰·검증 라운드를 돌린다.

## 튜닝 규칙
1. **범위를 고정하되 끝까지 하게 한다.** 레포 관례에 맞춰 테스트·문서·보조 파일을 덧붙이는 경향이 모든 effort에서 있다. 요청한 것만 원하면: "요청한 작업이 끝나고 확인되면 멈추고 보고. 요청 안 한 기능·테스트·파일·문서·리팩터 추가 금지. 도움이 될 것 같으면 끝에 제안만". 중간에 멈추는 게 문제면 앞에 "요청한 것이 모두 끝날 때까지 계속하고, 사용자 없이는 진행 불가하거나 위험한 단계 직전에만 멈춘다"를 붙인다.
2. **xhigh/max에서 자발적 리뷰 라운드 억제.** "작업이 끝나고 체크가 통과하면 멈추고 보고. 스스로 추가 리뷰·하드닝 라운드를 시작하거나 리뷰어 서브에이전트를 띄우지 말 것. 더 깊은 리뷰가 필요해 보이면 끝에 말만".
3. **아이디어·계획 요청은 거기서 멈추게.** 열린 요청("이걸로 뭘 할 수 있는지 보여줘")에 바로 발표자료·보고서를 만들기 시작할 수 있다. 아이디어·계획만 원하면 "아이디어/선택지/계획만 주고 멈춘다. 진행하라고 할 때까지 만들거나 바꾸지 않는다"를 명시.
4. **코딩 변경은 실제 검사로 검증.** 특히 low effort에서 테스트를 안 돌리고 완료 보고할 수 있다: "실행·빌드·타입체크 가능한 코드를 바꾸면 그 변경을 실제로 실행하는 검사(테스트/타입체커/빌드/변경된 명령)를 돌린 뒤에 완료 보고. 문법 검사나 시작도 못 한 검사는 불인정. 의존성만 없으면 프로젝트의 패키지 매니저·락파일로 설치(sudo·시스템 패키지 매니저 금지). 검사가 불가능하면 무엇을 왜 못 돌렸는지 밝힌다".
5. **최신 정보는 검색을 시킨다.** 허용·요구·요금처럼 바뀌었을 수 있는 내용을 학습 지식으로 답하는 경향. "도구 최소화" 같은 문구를 지우고, 검색 도구가 있으면 "확신이 있어도 바뀌었을 수 있는 세부(허용·요구·요금 등)는 검색으로 확인. 보고서·비교 같은 조사 작업은 현재 출처를 모아 작성"을 넣는다.
6. **몇 단계 계산이 필요한 JSON 출력이면 생각을 먼저.** 합계·규칙 적용·순위 같은 과제에서 생각 없이 바로 JSON을 내 정확도가 떨어진다. 시스템 프롬프트 끝에 "답하기 전에 문제를 끝까지 생각하라" 한 줄을 넣는다(구조화 출력 + adaptive thinking 기준). 구조화 출력이 없으면 파서는 응답의 **마지막 JSON 값**을 읽게 한다.
7. **진행 업데이트는 시점을 지정.** "최종 응답에 모아라"류 억제 문구는 지우고, 필요하면 "첫 도구 호출 전 할 일 한 줄, 끝에 짧은 요약"처럼 적는다. 장문의 정확한 텍스트(코드 스니펫·질문)를 중간에 보여야 하면 사용자 메시지 전송 도구를 주고 그 용도로만 쓰게 한다.
8. **중간 사용자 메시지·하네스 텍스트 배치.** 도구 결과 직후에 붙는 텍스트를 프롬프트 인젝션으로 의심할 수 있다. 사용자 텍스트를 `tool_result` 안에 넣지 않고, 하네스 알림과 사용자 말을 같은 블록에 섞지 않는다. 대화형 세션에선 도구 결과마다 토큰 카운트다운을 붙이지 않는다.
9. **톤·verbosity·프론트엔드는 Sonnet 5 원칙 유지.** 원하는 길이·톤은 긍정 예시로 명시. 프론트엔드는 구체 스펙(팔레트 hex·서체·레이아웃)을 주거나 시안 몇 개 중 하나를 고르게 한다.
10. **비전 작업엔 크롭/줌/코드 실행 도구.** 차트는 도구를 주는 것이 effort를 올리는 것보다 효과적(high+도구 > max 무도구). 기술 도면은 high 이상에서만 도구 효과.

## 하지 말 것
- **추론을 응답에 포함하라는 지시 금지** — `reasoning_extraction` 거부. 짧은 근거·작업 요약은 가능.
- **"생각을 덜 해라" 프롬프트로 지연 줄이기 금지** — 확실하지 않다. effort를 낮춘다.
- **between_tools 사용 시 "생각하지 마" 규칙 금지** — 내부 XML 태그 누출이 는다.

## 설정 (프롬프트 본문 아님 → ※ 메모로만)
- **effort 기본 `high`**(API 기본). 레벨이 재보정돼 Sonnet 5 설정을 그대로 가져오지 말고 재스윕. 에이전틱 코딩·다단계 도구 사용은 잘 정의된 작업이면 **medium**, 어렵거나 길면 high. 채팅·지연 민감 작업은 medium/low. xhigh/max는 품질 향상을 측정한 경우만.
- medium 이상에선 인사에도 짧게 생각한다. 생각을 줄이려면 effort를 낮춘다(low에선 단순 요청 대부분 생각 생략).
- thinking: adaptive(기본) 또는 `between_tools`(최저, high 이하에서만). `disabled`는 400. 도구 없는 추론 과제엔 adaptive 사용.
- `max_tokens`는 thinking 포함 — 에이전틱 코딩은 최대치 128,000 + 스트리밍.
- 진행 업데이트는 `thinking` 블록으로 오며 기본 display에선 비어 있음 → `display: "updates"`(beta).
- 토크나이저는 Sonnet 5와 동일. 분류기 거부 시 `stop_reason: "refusal"`(cyber/bio/frontier_llm/reasoning_extraction/general_harms); 서버측 fallback은 cyber·frontier_llm만 Sonnet 5로 재시도.
